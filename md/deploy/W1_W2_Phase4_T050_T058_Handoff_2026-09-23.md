## 2. W2 `0009` 격리 환경과 공동 삭제 검증

W1은 W2 SHA `dbd698f...` 기반 **로컬 전용** 이미지의 revision label과
`linux/amd64`를 확인했고, 그 이미지의 manifest digest는
`sha256:75328f723c8505175efb2dc8f43790092663de0960cf5fb2df6553f4ad755adc`이다.
별도 격리 W2 PostgreSQL은 `0009_private_deletion_receipt`까지 올려
테이블 두 개를 확인했다. W2 집중 회귀 **150 passed**, W1 command/ACK와
W2 실제 parser 교차 확인 결과는 위 증거 문서에 있다. 이 이미지는 ECR 게시나
운영 배포가 아니며, W1/W2 실제 삭제 명령·ACK 왕복을 시험하지 않았다.

**공동 실행이 필요한 행:** 계정/Project 삭제, 동일 명령 중복, stale epoch,
purge 실패 후 **같은 `deletion_id`·본문** 재전달, 늦은 worker replay,
다른 owner 격리, 공유 공용 Source 보존, W1/W2 재시작 후 수렴.
W1의 전용 target/dispatcher와 W2의 범위 계약·consumer가 갖춰지면 같은
source SHA·schema hash·DB head·immutable image digest·`run_id`로 실행하고
양측 count-only 증거를 대조한다. 로컬 검증 전 AWS 배포나 테스트 자원 정리를
완료로 표기하지 않는다.

## 4. W2에 요청하는 T050·T058 완료 산출물

1. **T050 (W2 소유):** `source_runtime.py`에 삭제 명령/ACK side effect,
   explicit rendered collector, health·inspect·bounded scheduler를 실제 operator와
   연결하고, W2의 새 clean full SHA·migration head·계약 해시·전체 회귀 결과를
   회신해 달라. 현 `dbd698f...`의 넓은 suite는 `RenderedCollector` 부재로
   8건 실패했다. T049의 체크 상태만으로 렌더링 완료를 인정할 수 없다.
2. **T058 (공동):** W1이 만든 하나의 실제 Job에서 direct-registration,
   실제 collection, commit-gate FINALIZE, W2 public outbox, W3 Source Authority와
   SQLite `READY`까지 관통해 달라. 같은 `run_id`에 CT15-01–09,
   W2→W3 duplicate/gap/conflict/replay/snapshot/restriction/Authority 오류,
   W3 재시작 및 W1/W2 상태·큐·DLQ count를 넣어
   `.runtime/evidence/w1-w2-w3-local.json`을 `PARTIAL`에서 공동 증거로 갱신한다.
   test-only in-memory broker 또는 과거 다른 SHA의 AWS 결과를 새 실행으로
   대신하지 않는다.
3. 양측이 full SHA·이미지 manifest digest·계약 해시·실행 ID·count/restart를
   독립 확인한 **후에만** 배포와 테스트 IAM/queue/profile/DB 정리를 진행하고,
   정리·잔여 자원을 각각 기록한다.

W1이 이번 문서에서 선언하는 것은 **경계 검증과 증거 제공 준비**뿐이다.
W1 전용 삭제 실제 dispatch/ACK, W2 T050, T058, 공동 승인, 서비스 READY는
모두 미완료다.
